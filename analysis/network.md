# REA network capture findings

Source: `analysis/rea-evidence.json`, `records[0].normalized_result`; Evidence ID `ev_569dba88ccdd6ced9b2db30ab16aba25d3215aad77c39212d127426c71621ac7`. The single scenario navigated a provider-owned Chromium 155.0.8059.85 to `https://www.clarissabuilds.com/`; no route clicks, audio playback, or other interactions occurred. Recorded duration 4,793ms. `network-summary.json` supplies every exact URL, transaction ID, status, resource type, event sequence, body digest/state, and header name. These are observations within that window, not an exhaustive network audit.

## Proven from captured runtime

- 32 GET transactions: 1 document, 1 stylesheet, 9 fonts, 14 scripts, and 7 fetch requests. All 32 yielded HTTP/API status 200 and `request-finished` events. There were 128 retained events (32 each request/response/request-finished/network-content), zero dropped events. No request-failed, console, or page-error events were recorded in the selected event families during this scenario.
- All 32 `url.origin` fields are `https://www.clarissabuilds.com`; 29 URLs use HTTPS and three use `blob:` with that same embedded origin. No external origin request was observed. External music/preview/GitHub links present in prefetched data did not load during this capture.
- Homepage document `/` and CSS `/_next/static/css/4d35b5fdca225d6e.css` returned 200. The 9 font requests are the nine preloaded WOFF2 subsets documented in `architecture.md`. The 10 initial script requests are webpack, React/Next runtime, main-app, both Three chunks, chunk 121, shared layout, chunk 176, and homepage route. Four more scripts are prefetched route dependencies listed below. The legacy `polyfills` file in the separately downloaded snapshot was not requested by this Chromium capture.
- `request-22`: `/earth_small.glb`, resource `fetch`, status 200. Body unavailable in this evidence due to `body-allocation-limit`; this is a capture allocation limitation, **not a failed GLB load**. Static layout code explicitly passes this URL to `GLTFLoader.load`. Three `blob:https://www.clarissabuilds.com/<UUID>` fetches (`request-26`–`28`) also returned 200; their body reads failed. Their relationship to GLB embedded image/object URLs is plausible but not proven by request ordering, which has no initiator stacks.
- Three RSC prefetches returned 200 `text/x-component` bodies: `request-23` `/projects?_rsc=3lb4g` (10,834 bytes), `request-24` `/writing?_rsc=3lb4g` (53,079 bytes), and `request-25` `/cabinet?_rsc=3lb4g` (13,829 bytes). Request header names include `next-router-prefetch`, `next-router-state-tree`, `next-url`, and `rsc`. These support Next Link prefetching; they do not indicate that the user navigated to those pages.
- Four additional script bodies returned 200: `request-29` `/_next/static/chunks/356-5cad24532f4c0e5d.js` (13,501 bytes); `request-30` `/_next/static/chunks/app/cabinet/page-682175f966b39262.js` (7,922 bytes); `request-31` `/_next/static/chunks/app/projects/page-39377cc8f42f2048.js` (6,010 bytes); `request-32` `/_next/static/chunks/app/writing/page-042cbead4bc198cd.js` (9,860 bytes).
- Response header **names** include `x-vercel-cache`, `x-vercel-id`, and, on page/RSC responses, `x-nextjs-prerender` and `x-nextjs-stale-time`. Header values were intentionally not captured; actual cache state, prerender flag values, edge region, and server header value cannot be asserted. Vercel delivery is an inference from the branded header names.

Seven useful textual response bodies were decoded from retained base64 into `analysis/runtime-client`; manifest entries preserve original URLs, transaction and response/content sequence IDs, bytes, and captured SHA-256. No new requests were made and the original `analysis/client` snapshot was unchanged. Offsets below are decoded character offsets, not byte offsets.

- `projects.rsc.txt` contains serialized project records (titles/descriptions/images/videos/stack/repository links), delivered as props to client module 6313. The word `supabase` at offset 7138 is a stack label **for a displayed project called straightline**, not evidence this portfolio calls Supabase. Projects client route module 6313 renders `FeaturedProjects` and `MoreProjects`; records come from props and it has no `fetch()` call. It displays local image/video paths, Next Image, GitHub/Devpost/live links, and a mouse-following image portal for extra projects. Route JS offset 3480 contains its local hover state and viewport-clamped portal placement.
- `cabinet.rsc.txt` contains serialized cabinet item records including title/by/kind/href/preview. Example offset 6114 has an `audio-ssl.itunes.apple.com` preview URL. Cabinet client route offset 4294 sets the existing audio element's `src=e.preview` and calls `play()` from a button click; this external source was not requested in the homepage-only scenario. Grid layout comes from the passed `items` prop and local `useMemo`; active playback/progress use local React state.
- Writing route chunk contains Canvas 2D orbital animation (`getContext("2d")` at 2728), and a small Three Earth thumbnail rendered to a 56×56 canvas (`new ...JeP` at ~5645), loaded from `/earth_small.glb`. Shared layout intentionally returns no background for `/writing`; this route supplies its own canvas. This is additional architecture evidence, not proof of its rendered appearance because no route navigation was performed.
- The four extracted route/dependency JS files contain no literal `fetch(`, `XMLHttpRequest`, `contentful`, `sanity`, `prismic`, or `wordpress` strings in bounded searches. The routes receive serialized content props; the origin of that content on the server or at build time remains hidden. Static data files/MDX/local content are plausible, but no source format or CMS can be proven from these payloads alone.

## Exact Three implementation identifiers

- `analysis/client/_next/static/chunks/bd904a5c-8bd26ce904b58ad0.js` offset **2877** contains `let n="178"`. Its tail at ~252178 registers `{detail:{revision:n}}` with Three DevTools, and assigns `window.__THREE__=n`. This proves shipped **Three.js r178**, not r179 or an inferred version from API style.
- `analysis/client/_next/static/chunks/b536a0f1-7811349744a45aca.js` module **7548** exports **`JeP:()=>nC`** near offset 0; class `nC` at ~289900 sets **`this.isWebGLRenderer=!0`** at offset **290211**. Shared layout imports module 7548 as `l` and creates `new l.JeP({antialias:!0,powerPreference:"low-power"})`. Thus this is the Three WebGLRenderer constructor, despite its minified export name. The renderer explicitly rejects a WebGL1 context, with error `WebGL 1 is not supported since r163.`

## Capture limitations / hidden details

- Overall REA completeness is `incomplete`, `missing_sections:["events"]`, `equality_eligible:false`, even though no events were dropped. Selected content unavailable states must be retained in conclusions.
- 24 response bodies were captured; 8 were unavailable: five `body-allocation-limit` (request-13 React chunk, request-14 Next chunk, request-16 Three core, request-17 Three renderer, request-22 Earth GLB) and three `body-read-failed` for blob fetches. Limits include 1,048,576-byte body allocation and configured 2,000,000 max body bytes. Separately fetched files in `analysis/client` supply static inspection for the large JS chunks; they must not be mislabeled as recovered captured response bodies.
- Network request/response **header values** and request bodies were not requested. Content media types/digests come from body metadata. Recorded Playwright `Response.body()` bytes are not guaranteed wire bytes; the provider warns that Playwright can perform a follow-up URL load when CDP lacks body bytes, so retained body identity does not prove it came from the original transaction.
- Request initiator stacks were unavailable. Event sequence represents provider receipt order, not causality. Body reads settle within five seconds each; no bodies are requested from unfinished responses. Screenshot, DOM and accessibility were requested at the end of this scenario; the screenshot is retained as `reference-desktop.png`. History and storage artifacts were not requested.
- The short homepage-only scenario cannot rule out later analytics, interaction-driven audio/network loads, APIs on other routes, server-side CMS calls, or build-time content generation. It supports only that none of these external requests were observed in this specific window.
